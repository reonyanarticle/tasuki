# FAQ

導入時に実際に聞かれた質問と答え。
詳細は各リンク先が正である。

## 実行の仕組み

**Q. worker が並行して動くとき、作業場所はどう分離されるのか。**
worker 1体につき git worktree 1つで完全に分離される(`isolation: worktree`、1対1)。
さらに checks-local と verifier は worker の worktree を信用せず、それぞれ自分の一時 worktree で検査と再実行を行う。
ぶつかり得るのは統合ブランチへの取り込みの瞬間だけで、orchestrator が到着順に直列で処理する([DESIGN.md](DESIGN.md))。

**Q. レイヤー計画コメントはどのモデルが書いているのか。**
orchestrator 自身である(`/tasuki:loop` を実行しているメインセッションのモデル)。
分割案は decomposer(Sonnet)が作るが、計画コメントの文章と図は orchestrator が `tasuki:plan-comment` skill に従って組み立てる。

**Q. 実装の仕様書はどこに残るのか。**
worker がコードを書く前に子 issue へ残す「実装方針」コメントがそれに当たる(作るもの、既存への接続、選択と理由、確かめ方)。
細部は仕様書ではなく draft PR の diff で見る設計である。

## issue と PR の見え方

**Q. 子 issue と子 PR が大量にできて一覧が汚れないか。**
子は機械の作業単位として `tasuki:child` ラベルが付き、統合ブランチへの取り込み時にループが子 issue を閉じる。
一覧は `is:open no:parent-issue` で親だけに絞れる。

**Q. 人間は子 PR もレビューするのか。**
しない。
子 PR はループが統合ブランチへ取り込み、人間の判断は親 PR のマージ1回に集約される。
子 PR は参照用に merged のまま残る([GATES.md](GATES.md) 観点 #24)。

**Q. 親 PR で何を承認すればよいのか。**
CI 全緑の後に親 PR の最後へ投稿される「承認のお願い」コメントを読む。
ループが裁量で決めた判断の一覧(どの子で決め、どこで検められたか付き)、やらなかったこと、リスクと戻し方が、コードを読まずに判断できる形でまとまる。

**Q. 親 PR はいつまで draft なのか。**
統合ゲートを通り、出荷前レビューに入るときに ready 化される。
draft は「組み立て中」の印である。

## 走行中の変化

**Q. 走行中に親の要件を変えたくなったら。**
親 issue 本文を編集して `loop:replan` ラベルを付ける。
実行中の作業を走り切らせてから、受理ゲートと分割ゲートを通して計画を作り直す(編集だけでは反映されない)。

**Q. ループ外で hotfix を main に入れてよいか。**
よい。
ループがレイヤーの区切りで default branch を統合ブランチへ取り込み、親 PR の承認前には必ず最新の default branch を含めた状態にする。

## 起票と外部からの issue

**Q. 親 issue の書き方に自信が無い。**
`/tasuki:draft` に要望を1文で伝えると、リポジトリの裏取りと質問で下書きを作り、受理ゲートと同じ基準で事前審査してから起票する。

**Q. public リポジトリで外部の人が issue を立てたら勝手に走らないか。**
走らない。
ループは `/tasuki:loop <親>` の明示起動でしか動かず、外部起票の親は maintainer が本文を読んで `tasuki:accepted` を付けない限り対象外である([SECURITY.md](SECURITY.md))。

**Q. 親 issue を同時に複数走らせられるか。**
v1 は同時1親である。
別の親は、先の親が停止状態(全子決着またはマージ待ち)になってから起動する。
