# tasuki の思想

tasuki の設計判断は、少数の原理から導かれている。
個々の機構(ゲート、契約、ロール)がなぜその形をしているかに迷ったら、ここに立ち返る。

## 抽象度は受け手基準で決まる

具体と抽象の往復では、各つなぎ目で「この出力は、受け手が追加の解釈なしに受け取れる抽象度か」の検証が必要になる。
抽象度は相対的であり、判定基準は常に受け手基準で決まる。
「十分に具体的な指示」という絶対基準は存在せず、受け手が誰か(decomposer か、worker か、人間か)によって適切な抽象度は変わる。

## バトンパスの4パターンと3値判定

仕事の受け渡しをリレーのバトンパスと見ると、渡し手の「引き渡し位置」と受け手の「待ち位置」の組み合わせで4パターンが生じ、成立するのは位置が一致する2パターンのみである。
ここから、ゲートの判定は絶対基準ではなく **受け手が宣言した待ち位置との照合** であり、判定結果は3値になる。

| 判定 | バトンパターン | 意味 |
|---|---|---|
| `PASS` | 位置一致 | 引き渡し位置=待ち位置 |
| `TOO_ABSTRACT` | バトンが落ちる | 曖昧語残り、受け入れ条件なし等 |
| `TOO_CONCRETE` | 受け手を追い抜く | 実装方式の過剰指定、生ログのままの報告等 |

`TOO_CONCRETE` が独立した不合格である点が、一般的な「品質チェック」との違いである。
実装方式まで指定された子 issue は worker の探索余地を奪い、生ログのままのレポートは読み手に解釈作業を押し付ける。
どちらも「詳しすぎる」ことによる受け渡しの失敗であり、「曖昧すぎる」失敗と対称に扱う。

## ズレ検知を仕組みに埋め込む

AI が実装からレビューまでを自律的に回すループでは、人間がズレを都度是正できない。
そこで、ズレ検知を仕組み(=ゲート)として各フェーズのつなぎ目に埋め込む。
ループの基本部品は、スケジュール実行(automations)、worktree 分離、skills、plugins/connectors、subagents の5つと、会話の外に置く記憶であり、tasuki では **記憶= GitHub issue** とする。

記憶を GitHub に置く選択には裏面がある。
issue コメントに書かれた判定や報告は監査ログとして永続化するため、機密の混入は取り消せない(レビュー観点「出力衛生」)。

## 役割はコンテキスト境界で切る

役割分割の原則は、作業の種類ではなく **コンテキスト境界** で切ることである。
フェーズ間の引き継ぎ物は「issue 本文だけで自己完結する契約」に強制されるため、境界での転送は契約のみになる。
抽象度ゲートは、判定装置であると同時にコンテキスト境界を作る装置を兼ねる。

この原則から、コンテキスト衛生の要件(レビュー観点「コンテキスト衛生」)が導かれる。
フェーズ実行、差し戻し再実行、ゲート判定はすべて新規セッションで始め、引き継ぎは契約(issue 本文+ verdict)のみとする。
継続セッションでの再試行はコンテキスト腐敗を再導入し、同じ誤りに固執する原因になる。
状態が issue に外部化されているため、セッションを捨てても失うものはない。

## 器も仕事の種類で切らない

役割と同じことが、契約という器にも当てはまる。
**仕事の型(開発、実験、調査)は、リポジトリ単位の属性ではなく issue 単位の性質である。**
型ごとに契約の器を分けると、器はリポジトリに1つしか置けないため、どちらを選んでももう一方の仕事に合わない契約が適用される。

型ごとの違いは3つの形で表す。

- **工程として扱う**:あらゆるタスクの中に現れる作業(調べ物など)は、独立したタスクの型にせず、各作業の1手順として行う。器に載せると、器の重さだけが乗る
- **条件付きのシグナルで表す**:「該当するのに書かれていない」の形で契約のシグナルに書く。該当しない仕事では発火せず、該当する仕事では判定に効く
- **導入先の override で表す**:その導入先で毎回問いかけたい欄は、repo override で必須欄に足す(型は導入先固有の情報であり、plugin 側の雛形が抱えるものではない)

この原則は、調査と実験の2つのプロファイルを作って撤回した経験から確定した([ROADMAP.md](ROADMAP.md) の「調査プロファイル(research)の試作と撤回」と「experiment プロファイルの廃止」)。
あわせて **抽象は、性質の異なる2例目を通してから固定する**。
1例しか無い時点で引いた境界には、その1例の形が焼き込まれる(プロファイルという抽象は、開発しか無い時点で引いたために「開発の形をした穴」になっていた)。
**近い双子は2例目に数えない。**
実験は開発の近い双子だったため、2例あっても器の欠陥は見えず、本当に違う3例目で初めて破綻した。

機構を足す前に、次の3つを問う。

1. **それはタスクの型か、工程か。** あらゆるタスクの中に現れるなら工程であり、器を与えない
2. **器の粒度と、性質の粒度は一致しているか。** リポジトリ単位の器に issue 単位の性質を入れると、どちらかの仕事に合わない
3. **今ある層で表せないか。** 契約のシグナル、導入先の override、既存の skill で表せるなら、新しい器は要らない

## 名前は駅伝から

tasuki(襷)の名前は駅伝に由来し、構成要素は次の対応で読み替えられる。

| 駅伝 | tasuki |
|---|---|
| 区間 | フェーズ |
| 走者 | agent |
| 中継所 | ゲート |
| 襷 | 契約 |
| 繰り上げスタート | 打ち切り条件 |
| 往路と復路 | 降りるゲート(抽象→具体)と昇るゲート(具体→抽象) |

「降りる」ゲート(受理から着手まで)は要件を具体化する方向の受け渡しを検め、「昇る」ゲート(成果と統合)は成果を抽象化して報告する方向の受け渡しを検める。

## 製造業と制御工学の語彙で設計する

本設計は工程設計と生産管理の体系と同型であり、以下の対応で読み替えられる。
命名や説明にはこの語彙を優先的に使う。

| 製造業、制御工学 | tasuki |
|---|---|
| 自働化(異常があれば止まる) | 抽象度ゲート、mechanical ゲート |
| 後工程はお客様 | 受け手基準の抽象度(waiting_level) |
| ポカヨケ | 門前払い、テンプレ必須欄 |
| 工程内検査と出荷検査の分担 | checks-local(反復中のローカル判定)と checks-ci(ready 化前の CI 判定) |
| 標準作業(標準なきところに改善なし) | skill、契約 YAML、初期 fixture |
| アンドン | triage inbox、通知 |
| なぜなぜ分析 | Fable 裁定の原因3分類 |
| かんばん(仕掛り制限) | WIP 制限(観点「スループット管理」) |
| ドラム・バッファー・ロープ(TOC、Goldratt『ザ・ゴール』) | 制約(人間の注意)を通る回数を親 PR の1回に最小化し、在庫の上限を親の予算(バッチサイズ)で縛る |
| 段取り替え時間の短縮 | ゲートレイテンシ、CI 速度(観点「フィードバック速度」) |
| 「検査、運搬、停滞は付加価値を生まない」(IE) | ゲート最小化、段階導入、滞留分析 |
| フィードバック制御の発振、ループゲイン | ゲートの発振検知(観点「ゲートの発振検知」) |
| むだ時間(遅延)による不安定化 | 検証遅延の安定性要件(観点「フィードバック速度」) |

この対応は装飾ではなく、設計判断の導出元である。
実際、段階導入([ROADMAP.md](ROADMAP.md))は「検査は付加価値を生まない」から、WIP 制限は TOC から、発振検知は制御工学から導かれている。

## 人間と AI の責任境界

ゲートが機械判定するのは「明示されているか」までである。
リスクを取るかどうかの判断は人間に残す。
マージは常に人間が実行し(最終ゲート)、判断原則の変更(axis-question)は必ず人間の承認を経由する。
機械検証できるものは AI へ、文脈依存の判断は人間へ、というのが責任の引き方である。
