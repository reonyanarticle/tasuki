# ゲート体系とレビュー観点カタログ

契約 YAML とテンプレ必須欄は、末尾のレビュー観点カタログから導出する。

## ゲート種別

| kind | verdict | 判定主体 |
|---|---|---|
| `abstraction` | `PASS` / `TOO_ABSTRACT` / `TOO_CONCRETE` | gate-reviewer(LLM、独立コンテキスト) |
| `mechanical` | `PASS` / `FAIL` + findings[severity] | CI(生成された workflow) |

abstraction ゲートは二段構成とする。

1. **門前払い**：テンプレ必須欄の空と欠落を機械チェックする。LLM 不要で、ループ入口の品質を秒オーダーで担保する
2. **契約照合**：gate-reviewer による3値判定。受け手が契約で宣言した `waiting_level` と照合する

3値判定の意味は [PHILOSOPHY.md](PHILOSOPHY.md) のバトンパスモデルを参照。

## ゲートカタログ

| ゲート | 識別子 | 位置 | kind | 主な検査 |
|---|---|---|---|---|
| 受理ゲート | `intake` | 親 issue 起票時 | abstraction | 課題価値とコスト予算の釣り合い、実現可能性の前提 |
| 分割ゲート | `split` | 親→子分割時 | abstraction | 良いタスクの4条件、依存の非循環、待ち位置整合 |
| 着手ゲート | `start` | 子 issue →実装前 | abstraction | 要件充足性(受け入れ条件、成功基準、打ち切り条件、実験条件)、予算欄 |
| 形式ゲート | `checks` | 反復中はローカル実行(`checks-local`)、ready 化前に CI で最終判定(`checks-ci`) | mechanical | lint / 整形 / 型 / テスト / セキュリティ |
| 成果ゲート | `outcome` | レポート→ issue | abstraction | 要件⇔結果の対応表(N対1)、生ログ排除 |
| 統合ゲート | `integration` | 全子完了→親 | abstraction | 子成果の親要件へのロールアップ、孤児要件なし |
| 最終ゲート | — | 親 PR のマージ | 人間 | 要件適合の最終判断。**default branch への反映は親 PR の人間マージのみ**(子 PR はループが統合ブランチへ取り込む) |

識別子はゲート名を英語にしたもので、契約ファイルの `gates[].id` と GitHub ラベル(`gate:<識別子>-passed` / `-returned`)に使う。
形式ゲートのサブゲートは `checks-lint` のように provider 名を続ける。

成果ゲートの判定は、レポートが契約の待ち位置(対応表と結論の形式)にあることの照合であり、人間のレポート読解(観点 #13)を置換しない。マージ前に人間がレポートを読む前提は成果ゲートを有効にした後も変わらない。
成果ゲートの reviewer(sonnet)は worker と同一モデルである。判定の独立性はモデルの違いではなくコンテキスト非共有で担保する(モデルを分けたい場合は契約の `reviewer:` 差し替えで行う)。

### 実装方針をどこに置くか

子 issue の待ち位置は「受け入れ条件つきで単独マージ可能な単位。**実装方式は未指定**」である。
したがって実装方式を issue 本文に書くと着手ゲートが `TOO_CONCRETE` で差し戻す。
一方で、人間が実装前に方向性を確かめる手段が無いと、出来上がってからしか止められない。

この2つは対立しない。
**要件と実装方針を別の場所に置く**ことで両立する。
置き場所は3つあり、それぞれ役割が異なる。

| 場所 | 役割 | 何を置くか |
|---|---|---|
| 親 issue | 全体の俯瞰と進行 | 各子が何を作るかの図、子の一覧、triage の所在 |
| 子 issue | その作業単位の要件と議論 | 本文= 受け入れ条件と成功基準、コメント= **実装方針** |
| draft PR | 実コードに基づく方向性のすり合わせ | 対応する親要件、受け入れ条件の充足、変更点 |

この分担は、1 issue = 1作業単位とし、その作業に関する要件と議論をその issue に集めるという原則に沿う。
親は俯瞰のための場所であり、詳細を集めると俯瞰できなくなる。

**実装方針のコメントは仕様書にしない。**
方向性が読み取れる最小限(作るもの、既存への接続、選択と理由、確かめ方)に留める。
文書で細部まですり合わせるより、**動くコードの diff の上ですり合わせるほうが早く正確**であり、それが draft PR の役割である。
方針コメントは「実装が始まる前に止められる」ことだけを担い、実質のレビューは出荷前レビュー(`2g`)が PR の差分に対して行う。

方針は要件ではないため、着手ゲートの判定対象にはならない。

### 分割ゲートの「良いタスクの4条件」

1. 単独でマージして壊れない
2. テストを同梱
3. 単独で revert できる
4. 一読で理解できる

加えて、次の組み合わせは **常に分ける** ことを差し戻し基準に含める。

- リファクタリングと機能追加
- ライブラリ更新と機能開発
- 性能改善と機能開発
- データ移行と機能開発
- feature flag の各段階(add → enable → remove)
- 相互に依存しない機能同士

## verdict スキーマ

```json
{
  "gate": "start",
  "verdict": "TOO_ABSTRACT",
  "confidence": "high",
  "model": "haiku",
  "reasons": ["受け入れ条件が『使いやすく』のまま", "打ち切り条件が未定義"],
  "return_to": "decomposer | worker | implementation",
  "questions": [
    {"type": "task-question", "to": "issue-author", "text": "..."},
    {"type": "axis-question", "to": "contract-pr", "text": "..."}
  ]
}
```

差し戻し先は2種類を区別する。
内容の不足は前フェーズへ、書き方の不足は同フェーズの再出力へ戻す。
成果ゲートでは `return_to` で書き分ける。書き方の不足は `worker`(レポートのみ再出力)、内容の不足は `implementation`(実装への差し戻し)とする。
前フェーズのロールが無効な段階(分割ゲートが無効なときの decomposer 等)では、差し戻しは該当 issue の起票者(人間)宛に読み替える。

**差し戻し再実行は必ず新規セッションで行う。**
前回セッションを継続せず、渡すのは契約+差し戻し verdict のみとする(コンテキスト衛生、観点 #16)。
継続セッションでの再試行はコンテキスト腐敗を再導入し、同じ誤りに固執する原因になる。

ゲートごとの判定モデルとエスカレーション規則は [DESIGN.md](DESIGN.md) のレイヤードレート構造を参照。

## レビュー観点カタログ

各観点がどのゲートで、何を、どう検査するかを一覧する。

| # | 観点 | 問い | ゲート | 不合格時 |
|---|---|---|---|---|
| 1 | 要件充足性 | 受け入れ条件と成功基準が揃い、曖昧語が残っていないか | 着手ゲート | 差し戻し or task-question |
| 2 | コスト妥当性 | 課題の価値に対し予算(最大反復数、実行コスト、想定時間)が釣り合うか | 受理ゲート | 人間へエスカレーション |
| 3 | 実現可能性、前提 | データ、環境、権限、依存ライブラリが揃っているか(実験ならデータ入手性) | 着手ゲート | task-question |
| 4 | 分割妥当性 | 4条件を満たすか、依存が非循環か | 分割ゲート | decomposer へ差し戻し |
| 5 | 抽象度整合(降り) | 引き渡し位置=待ち位置か | 分割ゲート, 着手ゲート | `TOO_ABSTRACT` / `TOO_CONCRETE` |
| 6 | 抽象度整合(昇り) | 各成果が元要件のどれに対応するか明示されているか(N対1) | 成果ゲート, 統合ゲート | 同上 |
| 7 | 形式品質 | lint、整形、型、テスト、セキュリティが閾値を満たすか | 形式ゲート | worker へ差し戻し |
| 8 | リスク、可逆性 | 影響範囲は把握されているか、revert 可能か、破壊的変更は明示されているか | 分割ゲート, PR 本文 | 人間の判断材料として提示 |
| 9 | 再現性 | 実験は seed、環境固定(lockfile)、データ版数の記録。開発はビルド再現 | 着手ゲートの必須欄+成果ゲートでの検証 | 差し戻し |
| 10 | セキュリティ、権限 | 質問の型と宛先が守られているか、原則変更が承認を経ているか | 常時 | axis-question 昇格 |
| 11 | 観測性 | 判定が issue コメントに残り、メトリクスが収集できるか | 機構要件 | — |
| 12 | 知識還流 | ループの学びが契約と skill に還流したか | ループ終端(任意) | — |
| 13 | 人間の関与 | 最終マージが人間か、差し戻し上限のエスカレーションが機能するか、成果物を人間が読んだか | 最終ゲート | — |
| 14 | 停滞検知 | 同一アクション反復、ピンポンパターン、進捗なきモノローグに陥っていないか | 実行中(watchdog) | 停止して人間へ報告 |
| 15 | 実行環境の隔離、権限最小化 | worker のツール allowlist は最小か、secrets は CI のみか、ネットワークと書き込み範囲は制限されているか | 機構要件 | — |
| 16 | コンテキスト衛生 | 各実行が新規セッションで始まり、引き継ぎが契約のみに限定されているか。コンテキスト予算は守られているか | 機構要件 | — |
| 17 | フィードバック速度 | ゲートのレイテンシは予算内か(PR ゲート CI は5〜10分以内、門前払いは秒オーダー) | 機構要件 | — |
| 18 | テストの信頼性 | worker が書いたテストは「壊れたら落ちる」か。既存テストの削除、skip、アサーション弱化がないか。期待値は仕様由来か | 形式ゲート(機械検知)+ 成果ゲート(レビュー観点) | worker へ差し戻し |
| 19 | 冪等性、再開可能性 | クラッシュや中断の後にラベルと issue コメントから状態復元して途中再開できるか。全操作は冪等か | 機構要件 | — |
| 20 | 並行整合性 | issue 割り当ての排他、orchestrator 二重起動の防止、レイヤー内のマージ順規約 | 機構要件 | — |
| 21 | 目的漂流の検知 | 反復のたびに「今の作業は元の issue 要件に向かっているか」を軽量チェック | 内側ループ(verifier に付随) | worker へ指摘、軌道修正 |
| 22 | 評価データの分離(実験) | 内側ループの反復は dev セットのみ、テストセット評価は最終報告の1回だけか | 着手ゲートの必須欄+ 成果ゲートでの検証 | 差し戻し |
| 23 | 出力衛生 | レポートと issue コメントに機密データ、個人情報、secrets が混入していないか | 成果ゲート + ログ経路のマスキング | 差し戻し |
| 24 | スループット管理(WIP 制限) | 仕掛り(未レビュー PR、未承認 axis-question)が人間レビュー帯域の閾値を超えていないか | orchestrator(起動制御) | 新規 worker 起動を停止 |
| 25 | ゲートの発振検知 | 同一箇所で TOO_ABSTRACT ⇄ TOO_CONCRETE が交互に出ていないか | gate-reviewer 履歴 | 契約不備として axis-question 昇格 |

## 観点の補足

**#2 コスト妥当性**：子 issue テンプレに予算欄(`max_iterations` / 想定実行コスト)を必須化する。
親の予算(コスト上限)との整合は、分割ゲートの `set_signals`(子件数、反復数の合計)で照合する。親予算が数値なら機械的に、prose なら reviewer の判断で確認する。機能そのものの費用や性能、速度の制約(非機能要件)は予算欄ではなく受け入れ条件、成功基準に測定可能な形で書き、verifier と着手 / 成果ゲートが照合する。
ループの token コストは運用形態で大きく変動するため、予算超過は自動でエスカレーションする。

**#8 リスク、可逆性**：ゲートが機械判定するのは「明示されているか」までとする。
リスクを取るかどうかの判断は人間に残す(責任境界は [PHILOSOPHY.md](PHILOSOPHY.md) 参照)。

**#12 知識還流**：差し戻しが繰り返された原因が契約の不備なら axis-question として契約 PR に、手順の不備なら skill 更新提案として出力する。
エージェントは毎セッション白紙で始まるため、学びを外部化しないとループが毎周同じ穴に落ちる。

**#14 停滞検知**：反復回数上限とは直交する停止装置である。
v1 の検知対象は orchestrator が観測できる事象(同一 issue への差し戻しの反復、verdict のピンポン、進捗のない再委譲)に限る。
agent セッション内部の反復は orchestrator から観測できないため、worker 側の打ち切り条件と watchdog(wall-clock)で守る。
ただし実験プロファイルでは、学習や推論ジョブの「待ち」を「停滞」と誤検知しないこと。
長時間ジョブはジョブ状態のポーリング(ハートビート)で待ちと判定し、watchdog の対象から除外する。

**#15 実行環境の隔離**：標準は権限最小化のみとする。
agent ごとのツール allowlist(gate-reviewer は読み取り専用、worker は担当 worktree 内の書き込みのみ)を敷き、secrets(API キー等)は CI 環境にのみ置いて worker セッションには渡さない。
コンテナ等のサンドボックス実行は v1 では実装しない(worker の隔離は worktree 分離とツール allowlist のみ)。worker 単位の契約オプション `sandbox: none | container` は v2 予約であり、信頼できない外部入力やサードパーティコードを扱うタスク向けに導入する。

**#16 コンテキスト衛生**：ループが長く回るほどコンテキスト腐敗が品質を落とす。
フェーズ実行、差し戻し再実行、ゲート判定はすべて新規セッションで始め、引き継ぎは契約(issue 本文+ verdict)のみとする。

**#17 フィードバック速度**：ループは反復×ゲート数だけ待ち時間を払う。
生成する CI workflow には依存キャッシュと並列 job を最初から焼き込み、PR ゲートを5〜10分以内に保つ(paths-ignore による job スキップは check-run を消して形式ゲート判定を fail-open にするため使わない)。
CI 最適化は計測ループとして扱う(最大の時間スライスを特定し、1つだけ変更して差分を検証する)。
なお #17 は効率要件であると同時に安定性要件でもある。
検証の遅延はフィードバック系を不安定化させる(むだ時間による不安定化)。

**#18 テストの信頼性(検証器の検証)**：verifier の判定はテストの質に上限を規定される。
AI 生成テストは「守ること」より「緑になること」に最適化しがちで、テスト対象ロジック自体のモック、実装出力の期待値化、断片的アサーションが典型的な false negative 源になる。
対策は3つ。

1. 形式ゲートに diff ベースの機械検知を置く(既存テストの削除、skip / xfail の追加、テストと型チェックの設定変更)。アサーション弱化(期待値の書き換え)は機械検知が難しいため、次項の成果ゲートのレビュー観点で検査する
2. 成果ゲートのレビュー観点に「期待値は仕様(issue の受け入れ条件)由来か、実装出力由来か」を追加する
3. テストは実装と同一 PR に同梱する(分割ゲートの4条件と整合)

依存追加の検知(lockfile diff)は形式ゲートの警告(非ブロック)として行う。flaky テストの検知(再実行で結果が変わるテストの隔離)は v2 とする。

**#19 / #20 冪等性、並行整合性**：本番のループはデモと違い、クラッシュは書き込みの途中で起き、リトライは半分だけ着地したステップを再実行する。
状態機械(ラベル遷移)は「読み→判定→書き」を再入可能に設計し、コメントと PR の作成は既存有無を確認してから行う。
orchestrator の二重起動は、親 issue の開始コメントの読み取りと書き込みで検知する(厳密な排他ではない)。読み取りから書き込みまでに隙があるため、同時起動が競合しうることは既知の制約であり、運用では親 issue ごとに1実行に留める。worker への issue 割り当ては assignee 設定を CAS 的に扱い、停止した実行が残した割り当ては経過時間で回収する。

**#21 目的漂流**：差し戻し対応を繰り返すうち、いつのまにか別の問題を解き始める失敗である。
局所的には各応答が一貫して見えるため気づきにくい。
verifier の判定に「成功基準への適合」だけでなく「元要件との方向一致」の軽量チェックを含め、漂流を検知したら着手ゲート相当の再照合に戻す。

**#22 評価データの分離**：「成功基準を満たすまで反復」は評価セットへの多重比較そのものであり、反復回数分だけ評価セットに過学習する。
experiment 契約の必須欄に dev / test 分離を入れ、テストセットでの評価は最終報告時の1回に制限する。
成果ゲートはレポートの数字がどちらのセット由来かの明記を要求する。

**#23 出力衛生**：状態を GitHub に置く設計の裏面として、issue コメントとレポートへの機密混入は監査ログとして永続化する。
レポートテンプレに「本文に掲載可能なデータの規約」(集計値のみ、生サンプル禁止等)を持たせ、生データはアクセス制御されたリンクのみとする。
secrets の CI 環境限定(#15)に加え、ログとコメント経路でのマスキングを機構要件とする。

**#24 スループット管理(TOC / DBR)**：システム全体のスループットは制約(ボトルネック)が決める。
本ループの制約は通常、人間レビュー帯域である。
制約をドラムとし、仕掛り上限(バッファ)を契約に持たせ、超過したら orchestrator が新規 worker 起動を止める(ロープ)。
非制約工程(worker 並列度)をいくら上げても、未レビュー PR が積み上がるだけでスループットは上がらない。
改善は TOC の5集中ステップに従う(制約を特定し、徹底活用し、他工程を制約に従属させ、制約を強化し、これを繰り返す)。

**#25 ゲートの発振(制御工学)**：同一箇所での TOO_ABSTRACT ⇄ TOO_CONCRETE の交互出現は、修正指示が過大(ループゲイン過大)か、契約の `waiting_level` 自体が曖昧で目標値が定まっていないことを示す。
worker への再差し戻しでは解決しないため、契約不備として axis-question に昇格する。
#14 停滞検知(同じ場所で止まる)と対をなす、「行き過ぎて往復する」側の検知である。
差し戻し verdict には前回 verdict との方向比較を含める。
