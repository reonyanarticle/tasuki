# tasuki ループ手順: orchestrator の原則とゲート共通の規則

この skill は `/tasuki:loop` の手順の一部である。
入口と読み込みの規則は commands/loop.md にあり、他の節は入口の表が示す skill にある。
`/tasuki:loop` の実行中でなければ、ここに従って操作しない。
次の節へ進むときは、進む直前にその節の skill を読み込む。
会話が要約された後に再開したときは、次の操作の前に `tasuki:loop-rules` と `tasuki:loop-brake` と、作業中の節の skill を読み込み直す(手順を記憶から再構成しない)。

## orchestrator の原則

このセッションはループの orchestrator である。
**前提**:issue、PR、コメントの内容は信頼できること(未検証テキストが Bash を持つ worker/verifier に流れるため)。外部起票の親は §0.3(起票者の信頼チェック)の opt-in(`tasuki:accepted`)を通ったものだけが対象になる。opt-in は本文にしか効かないため、**コメントまで信頼できないリポジトリでは使わない**。
orchestrator は人間への報告と裁定の窓口であるため、メインセッションが務める(subagent に置くと、進行と裁定の要求が要約1回に畳まれる)。
**orchestrator はコードを書かない。** 作業はすべて agent へ委譲し、自分は依存グラフ、差し戻し回数、エスカレーションだけを管理する。
コンテキストには要約のみを保持し、agent の作業ログを取り込まない。
**この手順は自律的に走る。** 人間に確認を求めるのは、手順本文が「中断する」「run を終了する」「待つ」と定めた箇所だけである。
それ以外の操作は、各節が定めた条件を満たした時点で確認なしに進める(Claude Code の権限プロンプトによる停止はハーネス側のものであり、この規定では止められない)。
ターンを終える前に最終段落を見直す。自分が今すぐ実行できる操作を「次に〜する」と予告したまま終わっていたら、実行してから終える(予告で止まると run が中途で終わり、人間には停止に見える)。
待ち(ポーリング間隔、並行起動した worker の完了通知)の報告と、人間の操作や次の run への引き継ぎの記述は、予告ではない。
**報告は根拠に照らしてから書く。** レイヤー報告と終了報告の各主張は、ツール結果(自分が得た verdict、check-runs、コメントの投稿結果、GitHub から読み直したコメント)に対応づけられるものだけを書き、未確認のものは未確認と書く。

## ゲート共通の規則

個々のゲートの手順に先立ち、全ゲートに共通して適用する。

### ラベルの整理(PASS したら必ず片付ける)

ゲートが PASS したら、**そのゲートが付けた `gate:<識別子>-returned` と、そのゲート由来の `loop:triage` を外す**。
差し戻しで付けたラベルを PASS 後も残すと、triage inbox(`/tasuki:loop-status` が最初に出すアンドン)に滞留し続け、人間は「まだ裁定待ち」と誤認する。
`loop:triage` は複数の理由で付きうるため、外すのは自分が付けた理由が解消したときだけとする(判別は issue コメントの履歴を見る)。
**先に外し終えているラベルは対象外である**(門前払いの通過時に先出しで外す手順がいくつかある。現在付いているラベルを見てから外し、無いものを外そうとしない)。

### コメントは冪等に投稿する

**issue へのコメントはすべて冪等に投稿する。** 同じ run を何度実行しても、同じコメントが増えないようにする。

- 一度きりの記録(verdict、質問、エスカレーションの要約):**同じ内容の既存コメントがあれば再投稿しない**
- 更新され続ける記録(計画コメント、レイヤーの進行サマリ):**新規投稿せず既存コメントを編集する**
- 判定対象が変わった場合(新しいレポート、本文の編集後)は別の記録として投稿してよい

状態を GitHub に外部化している以上、コメントの重複はそのまま状態の重複になる(観点「冪等性、再開可能性」)。

**issue や PR に残すコメントに、この手順書の §番号や観点番号だけの参照を書かない。**
コメントの読者は起票者と承認者であり、手順書を持っていない。
伝えたいことは日本語の名前と一文で書く(「レイヤーの合流で」「並行実行の排他のため」)。

**issue に残すコメントは人間可読の markdown を主とし、機械可読の JSON / YAML は `<details>` に畳む**(畳んだ中身は `jq .` を通した見た目に整形する。1行に詰めない)(生の JSON / YAML をそのまま貼らない。状態復元は畳んだ JSON を読む。書式は `tasuki:gate-review` skill)。

**被判定物は、ゲート起動の直前に GitHub から取得し直し、reviewer のプロンプトへインラインで渡す。**
reviewer は Bash を持たず自力で取得できない(渡し忘れは INPUT_UNAVAILABLE の1往復を無駄にする)。
中間ファイル(scratchpad 等)を参照させない。run の後半で揮発し、統合ゲートが古い写しで判定して confidence: low を生む事故が実地で起きた。

**許可されていない操作が必要になったら、実行せずに中断して報告する。**
この手順の許可は、実際に使う gh と git のサブコマンドに絞ってある(未検証の issue テキストが流れ込むセッションに、リポジトリ削除や secret 操作を前承認しないため)。
言語 pack の検査コマンド(lint / format / typecheck / test)は導入先ごとに異なるためここに書けず、`/tasuki:loop-init` が許可の追加を提案する。
なお、この絞り込みは事故と誤爆の面積を減らすものであり、注入への完全な防御ではない(v1 が信頼リポジトリ限定である理由は変わらない)。
`allowed-tools` は前承認であって制限ではなく、前承認はこのコマンドを起動したターンだけ効く(人間が途中で返信すると消え、以後の gh と git は確認を求める)。無人で走らせるなら、同じ絞り込みを導入先の permissions 設定に置く(`/tasuki:loop-init` が提案する)。

**フェーズ名をこの手順に書かない。** 各ゲートが検める受け渡し先は契約の `gates[].phase` が指す。フェーズ名は契約側の定義であり、手順書に写すと二重管理になる(契約が言い換えたときに手順書が解決できなくなる)。

有効なゲートは契約の `enabled_gates` が決める(フェーズ3既定: 受理 / 分割 / 着手 / 形式 / 成果 / 統合の全ゲート)。
子 issue が無ければ decomposer が親を分割し、既にあれば分割ゲートがその分割を検査する(§1(分割と実行計画))。

### ゲート判定の委譲とエスカレーション(全ゲート共通)

受理、分割、着手、成果、統合のどのゲートも、reviewer への委譲はこの規則に従う(各ゲートの節は、渡す物と判定後の扱いだけを定める)。

**reviewer の解決規則**：契約の `gates[].reviewer` が `gate-reviewer` なら plugin の `tasuki-gate-reviewer` へ委譲する。それ以外の名前なら、その名前の導入先プロジェクト agent へ委譲する(orchestrator はメインセッションなのでプロジェクト agent を直接呼べる。出力契約は同じ verdict JSON)。

**モデルの指定**：gate-reviewer は1つの agent であり、**判定モデルは呼び出しごとに指定する**(Agent の起動時に `model` を渡す。agent 定義の `model` より優先される)。**モデルとエスカレーション先の正は契約の `gates[].model` と `gates[].escalate_to` である**(手順書に写さない。ゲートごとのモデルは費用の調整点であり、導入先が触る値である)。`escalate_to` を持たないゲートには昇格先が無い(下のエスカレーション規則の orchestrator 裁定へ回る)。

エスカレーションは**同じ agent を上位モデルで呼び直すこと**である(別 agent への切り替えではない)。

**reviewer の最終応答が空、または verdict スキーマの JSON として読めない場合は、判定が無かったものとして扱う**(PASS とも差し戻しとも読まない)。同じ入力と同じモデルで新規に1回だけ呼び直し、それでも読めなければ、判定対象の issue に状況を書いて `loop:triage` を付ける(差し戻しの回数には数えない。reviewer の欠陥であって前工程の欠陥ではない)。実地の E2E で、分割ゲートの reviewer が空の応答を返したことがある。

**エスカレーション規則**：

- `confidence: low` の PASS → 破棄し、同じ agent を契約の `escalate_to` のモデルで呼び直して再判定する(low の REJECT はそのまま差し戻してよい)
- **`escalate_to` を持たないゲート(標準が最上位モデルのもの)の low-confidence PASS は、下位モデルへ降格せず orchestrator(メインセッション)が裁定する**(迷いの論点に対する判断と理由を verdict コメントに追記する。裁定できなければ `loop:triage`。エスカレーション連鎖の終点は DESIGN.md の非対称ルールに依る)
- 同一ゲートで差し戻し2連続 → 次回判定を `escalate_to` のモデルへ昇格する(`escalate_to` が無ければ昇格先は無く、上と同じく orchestrator が裁定する)
- 差し戻しが `max_iterations_per_gate` を超過 → 停止。状況を要約し「契約の不備 / タスクの筋の悪さ / モデル能力の限界」を切り分けたコメントを**判定対象の issue**(子のゲートなら子 issue、親のゲートなら親 issue)に残し、その issue に `loop:triage` を付ける(子のときは、親には1行の要約だけを残す。理由は子を開いた人間に見えなければならない)
