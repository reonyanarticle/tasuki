# tasuki ループ手順: §3(レイヤーの合流と統合ゲート)

この skill は `/tasuki:loop` の手順の一部である。
入口と読み込みの規則は commands/loop.md にあり、他の節は入口の表が示す skill にある。
`/tasuki:loop` の実行中でなければ、ここに従って操作しない。
次の節へ進むときは、進む直前にその節の skill を読み込む。
会話が要約された後に再開したときは、次の操作の前に `tasuki:loop-rules` と `tasuki:loop-brake` と、作業中の節の skill を読み込み直す(手順を記憶から再構成しない)。

## 3. レイヤーの合流と統合ゲート

### 3a. レイヤーの合流

現在レイヤーの全子 issue が停止状態(統合ブランチへ取り込み済み / `loop:triage` / 差し戻し待ち / WIP 待ち)になったら、レイヤーの状況を親 issue に報告し、§1c(依存グラフとレイヤー)の計画コメントを最新の状態に更新する(図を描いている場合は状態色も含めて更新する)。
このレイヤー報告は、**人間が途中で覗いてよい任意のチェックポイント**である(読む義務は無い。読まなくてもループは正しく進む)。方向がおかしいと感じたら、`loop:pause` を付けて止めるか、該当する子の実装方針コメントに返信して指摘する(人間の是正を親 PR の1点まで遅らせないための、覗ける窓)。
全子が取り込み済みの場合のみ「レイヤー完了」と呼び、差し戻し待ちや triage が残る場合は「レイヤー未完了(人間対応待ち)」として残項目を列挙する。

**再計画の発効点。**
親に `loop:replan` が付いていれば、次レイヤーへ進む前に §1d(再計画)を実行する(現在レイヤーは停止状態に達しており、実行中の worker が居ない)。

**default branch の取り込み(定点1)。**
次レイヤーへ進む前に、default branch が統合ブランチの merge-base より進んでいないかを確認する。
進んでいれば、**§1c(依存グラフとレイヤー)と同じ一時 worktree の中で** 統合ブランチの最新を取り込み元にして default branch を merge し、push まで行う(`git fetch origin` の後に `git checkout --detach origin/loop/parent-<親番号>`、`git merge --no-edit origin/<default branch>`、**`git push origin HEAD:loop/parent-<親番号>`**。ローカルのブランチを使わないのは、人間が統合ブランチへ直接 push した後でも古い写しから merge して push を拒否されないためである)(push しないと次レイヤーの worker が origin から古い統合ブランチを取る)。rebase はしない(子 PR が参照するコミットを書き換えないため)。
**merge が conflict したら、その場で `git merge --abort` して作業ツリーを元に戻してから**、下の「統合ブランチが直せない状態になったとき」へ回す(コンフリクト状態の worktree を残すと、次の run の checks-local が解決できない状態から始まる)。
ループ外の開発(hotfix 等)はこの定点で合流し、hotfix 側に特別な経路は要らない(人間は普通に default branch へマージしてよい)。
取り込み後は統合ブランチ上で checks-local を再実行する。
このとき 2d のテスト改変検知は、default branch 側から来た変更(merge の相手側のコミット由来)を差し戻し理由にしない(hotfix が正当に変更したテストを worker の改変と誤認しない)。

**統合ブランチが直せない状態になったとき(conflict、または checks-local が赤)。**
**ループは自分で直さず、止めて人間に渡す。**
親 issue に、何が衝突したか(または何の検査が赤か)と再現コマンドを書いたコメントを冪等に残し、`loop:triage` を付けて run を終了する。
人間が統合ブランチを直して `loop:triage` を外すと、次の run が続きから走る。

**自己修復の機構をループに持たせない。**
統合ブランチの補修は親要件に対応しない工程であり、子 issue(親要件に対応する作業単位)という器に入れると粒度が合わない。
実際に入れてみると、着手ゲート、分割ゲートの再判定、再計画の差分分割、差し戻し先の読み替えのそれぞれに読み替え節が要り、読み替え節1つが抽象の漏れ1つになった(判断基準は「器も仕事の種類で切らない」)。
この経路は実走の例がまだ無い。止めておけば「何回、どの形で起きるか」が triage に記録され、それが設計の材料になる。


**次レイヤーへは、現在レイヤーの全子が統合ブランチへ取り込まれたら進む。**
合流点は統合ブランチの更新であり、人間のマージを待たない(人間の判断は親 PR の1回に集約されている)。
1件取り込むごとに、統合ブランチ上で checks-local を再実行する(古い base への判定のまま重ねない)。
取り込み後に赤になった場合、その子の PR は既にマージ済みで子 issue も close 済みのため、2d には戻せない。**定点1と同じ扱いで、止めて人間に渡す**(上の「統合ブランチが直せない状態になったとき」)。
次レイヤーの worker は、更新された統合ブランチから worktree を作る。

### 3b. 統合ゲート

最終レイヤーまで完了し、**全子 issue が決着(統合ブランチへの取り込み、または人間による不採用クローズ)し、かつ親 issue に `gate:integration-passed` が無ければ**判定する(3c(出荷前レビュー)の差し戻しで戻ってくるたびに reviewer を呼び直さない)。
ただし `gate:integration-returned` が付いている場合は、**子集合の変化(子の追加、決着状態の変化)があるか**、親本文の `lastEditedAt` が最終統合ゲートの verdict より新しいときだけ再判定する(§0.10(受理ゲート)と §1b(分割ゲート)と同じガード)。
差し戻し直後は全子が決着済みのままなので、ガードが無いと run のたびに同じ孤児 verdict を出して decomposer まで呼び直す。両者はどちらも closed になるため、**取り込みの完了コメントの有無で区別する**(完了コメントが無い closed は不採用として扱う)。
ただし「replan により撤回」コメント付きの closed は再計画による撤回であり、不採用として扱わない(対応する親要件は §1d(再計画)の本文編集で消えており、未充足の材料にならない)。不採用クローズされた子の親要件は「未充足」として統合ゲートに渡し、要件の縮小(親本文の修正)か追加分割かを人間に問う材料にする。
統合ゲートが照合する契約は `gates.integration.phase` が指すフェーズの `receives` 定義(全親要件⇔子成果の対応、孤児の親要件なし)である。
**ゲート共通の規則の「ゲート判定の委譲とエスカレーション」**に従って委譲する(モデルは契約の `gates.integration.model`)。渡すのは次の4つだけ。

- 親 issue 本文(要件)
- 契約の `gates.integration.phase` が指すフェーズの `receives` 定義
- 各子 issue の最終レポート(リンクと要旨)
- 子 issue の完了状態一覧

verdict は親 issue に人間可読の markdown で記録し、機械可読の JSON は `<details>` に畳む(`tasuki:gate-review` skill の書式。生の JSON を貼らない。冪等)。

- **PASS** → `gate:integration-passed` を付けてラベルを片付け(共通規則)、親要件⇔子成果のロールアップ表を親 issue にコメントし(冪等)、§3c(出荷前レビュー)へ進む
- **差し戻し** → 孤児の親要件(どの子成果にも対応しない要件)を列挙し、`gate:integration-returned` と `loop:triage` を付ける。不足を埋める追加子 issue の分割案を decomposer に**差分分割モード**で作らせ、提案として親にコメントする(旧分割案 YAML と子の決着状態一覧は §1d(再計画)と同じ要領で渡し、**統合ゲートの verdict(孤児と判定された親要件の列挙)も渡す**。渡さないと decomposer はどの要件が欠けたか分からず全体を導出し直す)。
  **起票は人間承認後である。承認のシグナルは `loop:replan` の付与と定める。**
  人間が提案を読み、必要なら親本文を直して `loop:replan` を付ける。
  次の run は §1d(再計画)の経路で、その提案をそのまま子 issue として起票する。
  提案コメントにはこの操作を1行で書く(コメントの読者は手順書を持っていない)。

### 3c. 出荷前レビュー(親 PR、最終コード評価)

**実行条件**:統合ゲートが PASS し、親 PR(統合ブランチ → default branch)の check-runs が全て成功し、**統合ブランチの merge-base が default branch の先端と一致していること**(定点2)。
一致していなければ、先に §3a(レイヤーの合流)の定点1と同じ手順で default branch を取り込み、CI の全緑を確認し直してから入る。
親 PR の check-runs の読み方は §2g(出荷ゲート)の分類に従う(未完了は待つ。0件と `skipped` は成功とみなさない。`cancelled` は1回だけ走らせ直す)。失敗した job があれば、§3a(レイヤーの合流)の「統合ブランチが直せない状態になったとき」と同じく、止めて人間に渡す(直す先の子は close 済みである)。
実行条件を満たしたら、親 PR の CI の失敗(下)や §3a(レイヤーの合流)の「統合ブランチが直せない状態」で付けた `loop:triage` が残っていれば外す(止めた理由が解消している)。
人間が承認する「全差分」を、マージで実際に default branch へ入るものと一致させるためである(base が古いままレビューすると、承認した差分とマージ結果がずれる)。
対象は**親 PR の全差分**(そのフィーチャーの完成形)である。子 PR ごとには行わない(人間が見る場所を親 PR に集約する)。

**3c は「機械のレビュー → 人間への承認依頼」の順で進む。**
レビューが修正の要る所見を出せば人間に渡して止まるため、承認材料の投稿と ready 化はレビューを終えてから行う(先に出すと、直後に止まる前提の「承認してほしい」の文言だけが残る)。

### 3c-1. レビューの実行

**再入時は、レビューを起動する前に、下の「状態の持ち方」で有効なレビュー結果があるかを判定する**(有効な結果があればレビューを起動せず、その分岐に従う。判定を後に回すと、run のたびにレビューを起動し直す)。
**レビューは orchestrator が subagent で自動実行する**(人間の起動を待たない。人間の関与は結果を読んで親 PR をマージする1回に保つ)。
これは動的なワークフローではなく固定のファンアウトであり、**規模は契約の `preship_review` で制御する**(レビュー subagent 1体あたりの消費は無視できないため、常時5体を固定しない)。

- `mode: full` → 常に観点別5セッション
- `mode: scaled`(既定) → 親 PR の diff 行数が `fanout_threshold_lines` 未満なら **1セッションに5観点を順に**回させる(小さい diff では観点の薄まりのリスクが低い)。以上なら観点別5セッションに分ける
- `mode: manual` → 自動実行しない。人間へレビューの起動を案内し、その出力を待つ(必要なタイミングでだけコストを払う運用)

1. **観点ごと(scaled の小規模時は1セッション)にレビュー subagent(新規セッション)を起動し、下表の5観点を1観点ずつ回す**(大きい diff を一度に渡すと観点が薄まり、指摘が表層に寄る。maker のコンテキストを渡さない=このレビューも checker 分離)。レビュー subagent は**汎用 agent**(専用の agent 種別を持たない。tasuki は reviewer agent を同梱しない)を **sonnet** で起動する(所見の採否は orchestrator が判断するため、ここに上位モデルは使わない)。渡すのは親 PR の全 diff、親 issue の完了の定義、各子 issue の受け入れ条件と成功基準の欄、担当観点の定義のみ(観点「正しさと境界条件」と「テストの妥当性」が AC / SC を照合するため)。導入先に `/code-review` 等のレビューコマンドが導入されていれば、**その起動は人間に案内する**(orchestrator は自分で呼ばない。この手順に必要な操作は `allowed-tools` に列挙してあり、任意のコマンドを起動できる口はそこに含めない。別建ての課金が発生するコマンドもある)
2. 返った所見を**そのまま信じない**。orchestrator が対象コードを読み、再現条件を確かめ、**実在するものだけ**を採用する(古いツリーに対する所見や、仕様どおりの挙動を欠陥と誤認した所見が混ざる)
3. 採用の判断を終えたら、下の「状態の持ち方」の**レビュー結果コメント**を親 PR に1件投稿する(レビュー subagent には投稿させない。採用前の所見を人間に見せず、観点ごとに結果が散らばらないようにする)。採用した所見に修正が要るなら、**止めて人間に渡す**。**先にレビュー開始コメントへ「修正の要る所見あり(対象の SHA)」と書き足し、次に親 issue に `loop:triage` を付け、その後で**結果コメント(所見と対象箇所)を投稿して run を終了する(順序が要件である。逆順で間に落ちると、次の run は「所見の結果があるのに triage が無い」状態を見て、人間が受け入れたと誤認する)(**close 済みの子へ差し戻さない**。3c(出荷前レビュー)に入る時点で全子 issue は取り込み時に close 済みで、その PR も merged である。merged な PR のブランチに積んでも 2g の冪等分岐が「既に merged」として後始末だけを行い、修正が統合ブランチに一度も入らないまま完了扱いになる)。**所見をループが自分で直す経路は v1 では持たない**(直す先が close 済みの子しかなく、器を合わせると読み替え節が増える)
4. **セキュリティ**:変更が認証、権限、外部入力、秘密情報、CI 設定のいずれかに触れる場合、または契約の `enabled_gates` に `checks-security` がある場合は、`/claude-security:claude-security` の実行を人間に案内する(これは subagent 化しない。別建ての API 課金が人間の判断に属するため)
5. 所見の処理が終わったら 3c-2 へ進む。**マージは人間が行う**(このマージが default branch への唯一の反映点。子 issue は取り込み時に close 済みで、`Closes` 列挙は close し損ねの保険)。親 issue の close も人間が行う(完了の定義への最終適合は人間の判断)

### 3c-2. 承認材料の投稿と ready 化(レビュー完了後)

1. **親 PR の本文を承認者向けに最終化する。** 親 PR は監査の記録ではなく**承認の道具**である。本文は2段で構成する。

   **前半(作成時から置く): 大観。** 何が変わるか(利用者に見える変化と、内部だけの変化を分けて書く)と、計画コメントへのリンク。組み立て中はここまでしか書かない。

   **承認のための材料は、本文の編集ではなく「新規コメント」として投稿する**(レビューが所見なし、または所見の修正を取り込み終えてから)。人間はタイムラインを下へ読むため、最後に現れるコメントが「いま読むべきもの」の自然な置き場である。本文の編集は静かに書き換わるだけで、読み手に届かない。本文側には大観と「承認材料は最後のコメント」への一言だけを残す。
   検証とレビューが通る前に承認の文言を出すと、直後に差し戻す前提の「承認してほしい」が世に出る。順序は、機械の検証が先、人間への依頼が後である。
   このコメントは1件だけとし、差し戻し後の再入では同じコメントを編集して更新する(冪等)。

   欄は契約の `parent_pr_required_fields` を正とし、次の要領で埋める(欄名を手順書側で増やさない)。

   - **検証の要約**(契約の「何が変わるか」の前置き):check-runs 全緑、統合ゲート PASS、出荷前レビューの結果を1行で(承認の前提が揃った、という宣言)
   - **承認してほしい判断**:各子の実装方針コメントの「選択と理由」から、親 issue の要件に書かれていない裁量の決定を集めて列挙する(**maker が実装方針コメントを持たない契約では、その maker の第1手コメントを入力元にする**)。**各判断に「どの子(#N)で決めたか」と「どこで検められたか」(検めたゲートや検証したテスト)を必ず添える**。読み手が「この判断は誰がいつ下し、何が担保しているか」を1行で辿れることが、コードを読まずに承認できる条件である
   - **やらなかったこと**:スコープ外に残した既知の課題。**どの子の作業で見つかったかを添える**(次の親 issue の種として辿れるように)。あわせて、各項目を次の親 issue として起票できる下書き(親テンプレの必須欄のうち、背景と目的を発見時の文脈から埋めたもの)を `<details>` に畳んで添える。**起票はしない**(リポジトリに issue を増やすかは人間の判断。機械はコピーして起票できる状態までを用意する)
   - **リスクと戻し方**:壊れたときに何が起き、どう戻すか
   - **対応 issue**:`Closes` の列挙(取り込み時に close 済みの保険)
2. **親 PR を ready 化する。** draft は「組み立て中」の印であり、統合ゲートを通った時点で組み立ては終わっている。人間に判断を求める PR が draft のままなのは誤った合図になる(ready 化はレビューを終えてからなので、修正の要る所見が出た場合は draft のまま人間に渡る)。

**状態の持ち方**:3c に入るとき、**親 issue** に `loop:review` ラベルを付け、**同時に親 PR へレビュー開始コメントを1件残す**(冪等。ラベルは付与時刻を持たないため、待ち時間の起点はこのコメントの時刻とする)。ready 化して人間のマージ待ちに入るときに外す(修正の要る所見で止まる間は付けたままにする。3c の途中であることの印である)。

**レビュー結果コメント**は orchestrator が採用の判断の後に投稿する1件であり、見出し「出荷前レビューの結果」で始め、**レビューした統合ブランチの head の SHA** と、判定(「所見なし」または「修正の要る所見あり」)と、採用した所見を書く(所見ゼロの場合も「所見なし」と1件残す。**レビュー結果は親 PR のコメントに残す**)。`manual` では人間が起動したレビューの出力を入力とし、それを読んだ orchestrator が同じ形で投稿する(人間の書いたコメントを結果として数えない)。レビューの起動を案内するときに対象の head の SHA を書き、出力は見出し「出荷前レビューの出力」とその SHA を付けて親 PR に貼ってもらう。入力に数えるのは、最新の結果コメントより後に貼られ、SHA が現在の head と一致する出力だけである(push より前の出力を新しい head の結果にしない)。
再入時は、**最新の**レビュー結果コメントを、統合ブランチの現在の head と SHA で比べる(時刻では比べない。コミット時刻は push する側が決める)。

- 結果の SHA が head と一致する、または結果の SHA から head までの first-parent の履歴(`git log --first-parent --format='%H %P' <結果の SHA>..<head>`)が、**衝突の解消を含まない** default branch の取り込みだけである(2つ目の親が `origin/<default branch>` の祖先である(`git merge-base --is-ancestor` で確かめる)merge commit で、かつ `git show --cc --format= <merge commit>` が空であるもの。どちらの親とも違う変更を持つ merge は、人間が書いた解消のコードを含むのでレビューし直す) → **結果は有効**である。下の分岐へ進む(定点2の取り込みのたびにレビューをやり直さず、人間の受け入れも引き継ぐ)
- それ以外(人間が修正を push した等) → 結果は古い。この head に対してレビューを起動し直す(`manual` では、この head の SHA を書いてレビューの起動を案内し直す)

有効な結果は、判定と `loop:triage` で分岐する。

- 「所見なし」→ 所見で付けた `loop:triage`(前の結果コメント、またはレビュー開始コメントの「修正の要る所見あり」の書き足しが理由を示すもの)が残っていれば外し(止めた理由が解消した)、3c-2 へ進む(承認材料の投稿と ready 化が済んでいれば、そのまま人間のマージ待ち)
- 「修正の要る所見あり」で `loop:triage` が付いている → 人間待ちを維持する(再投稿しない)
- 「修正の要る所見あり」で **`loop:triage` が外されている** → 人間が所見を直さずに受け入れたとみなして 3c-2 へ進む。承認材料の「検証の要約」に、受け入れられた所見があることを1行で書く(所見の triage は結果コメントより先に付け、ループは外さないので、外れているなら外したのは人間である。ここで付け直すと、所見を受け入れる人間の手段が無くなる)

親 PR を ready 化した後に head が変わり、取り直したレビューで修正の要る所見が出たら、`gh pr ready --undo` で draft に戻してから上記3のとおり止める(承認を求めたまま所見を抱えた状態にしない)。

**有効な結果コメントが無い場合の扱いは契約の `preship_review.mode` で分かれる**(結果を推測しない点は共通)。

- `full` / `scaled`(orchestrator が自動実行する設定): この head のレビューが結果を残す前に落ちたということなので、**レビューを起動し直す**(待ち続けると、ラベルだけが付いた状態で親 PR が draft のまま無期限に止まり、triage にも上がらない)。**起動し直しは同じ head の SHA について `max_iterations_per_gate` まで**とし、超えたら `loop:triage` を付けて中断する(結果を残せない構造的な理由があるときに、run のたびに同じ位置へ戻る反復を止める。起動し直すたびにレビュー開始コメントを編集して SHA ごとの試行回数を書き足し、その数で判定する。開始コメントは冪等に1件のままなので、件数では数えられない。人間の修正で head が変われば数え直す)
- `manual`(人間が起動する設定): レビュー待ちを維持する。ただし、レビュー開始コメントと最新の結果コメントのうち新しいほうからの経過が `stale_assignment_minutes` を超えたら `loop:triage` を付けて可視化する(沈黙した待ちを inbox に出す)

沈黙の可視化(上の `manual` と起動し直しの上限超過)で付けた `loop:triage` は、結果コメントを投稿するときに、判定が「所見なし」なら外し、「修正の要る所見あり」ならそのまま所見による停止の triage として引き継ぐ(共通規則のラベルの整理は verdict を持つゲート向けであり、3c は verdict を持たないため、外す条件をここで定める。所見があるのに外すと、次の run が人間の受け入れと誤認する)。
修正の要る所見で付けた `loop:triage` は、上の「所見なし」の分岐で外す場合を除き、ループが外さない(外すのは人間であり、外したことが受け入れの合図になる)。

**レビュー観点(5つ)**

出典は2つある。
[Google のコードレビュー指針](https://google.github.io/eng-practices/review/reviewer/looking-for.html)(design を最重要とし、functionality、complexity、tests、naming と続く)と、[Findy Library の Code Review](https://lib.findy.co.jp/development/code-review.md)「What review verifies」(functional / non-functional / design & architecture / test suite / readability の5観点)である。
両者はほぼ同じ範囲を指しており、これを tasuki の1親 issue ぶんの変更に合わせて畳んだ。

| # | 観点 | 見るもの |
|---|---|---|
| 1 | 設計と統合 | 変更を置いた場所と抽象の粒度。既存との重複、責務のはみ出し、三層構造(core / pack / repo override)の越境 |
| 2 | 正しさと境界条件 | 親 issue の完了の定義と各子の受け入れ条件を実際に満たすか。エラー経路、空と null、冪等性、並行時の競合、失敗時の後始末 |
| 3 | テストの妥当性 | AC / SC に対応するテストがあるか。実装出力を写しただけの期待値になっていないか。**その修正を revert したらテストが赤くなるか** |
| 4 | 複雑さと可読性 | 過剰な一般化、次に読む人が追えるか、命名とコメントが「なぜ」を語っているか |
| 5 | 運用影響 | revert 可否、移行と後方互換、失敗が観測できるか、性能と費用の非機能要件を満たすか |

観点を増やしたくなったら、増やす前に「その観点で過去に見逃した実例があるか」を確認する(観点は多いほど薄まる)。
