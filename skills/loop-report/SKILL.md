# レポート作成手順

レポートは「昇り」の受け渡しであり、受け手(issue 起票者と統合ゲート)の待ち位置は「要件⇔結果の対応表と結論。生データは添付リンクのみ」である。
生ログをそのまま貼る報告は TOO_CONCRETE として差し戻される。

## 必須構成

1. **要件⇔結果の対応表**：子 issue の受け入れ条件、成功基準の各項目に、結果を1行で対応づける(N対1)。どの要件にも対応しない結果、どの結果にも対応しない要件(孤児要件)を残さない。要件 ID は子 issue 本文の並び順で受け入れ条件を AC-1、AC-2 …、成功基準を SC-1 … と採番し、**再出力時も同じ採番を維持する**(振り直すと差し戻し履歴、発振検知との対応が壊れる)
2. **結論**：成功基準を満たしたか、打ち切り条件に達したかを冒頭で言い切る
3. **再現手順**：コマンドと環境。実験は seed、環境固定(lockfile)、データ版数を含める(観点「再現性」)
4. **期待値の根拠**：対応表の各要件について、テストの期待値が仕様(受け入れ条件)のどの記述に由来するかを1行ずつ書く(実装出力を写した期待値でないことを示す。観点「テストの信頼性」)
5. **生データへのリンク**：本文には集計値のみを載せ、生データはアクセス制御されたリンクにする
6. **参照した skill と委譲した subagent**：このタスクで読み込んだ skill(プロジェクト skill を含む)と、委譲したプロジェクト subagent を名前で列挙する(無ければ「なし」)。読み手が「この成果はどの規約と道具を前提に作られたか」を辿れるようにするためであり、承認材料の「どこで検められたか」の裏付けにもなる

対応表の形式:

| 要件 ID | 要件 | 結果 | 判定 |
|---|---|---|---|
| AC-1 | (受け入れ条件を引用) | (1行の結果) | 達成 / 未達 / 部分達成 |

## experiment プロファイルの追加要件

- 本文中のすべての数字に由来セット(dev / test)を明記する(観点「評価データの分離」)
- テストセットの数字は最終報告の1回だけ。内側ループの反復で参照した数字は dev セットであることを明示する

## 出力衛生(観点「出力衛生」)

レポートと issue コメントは監査ログとして永続化するため、混入は取り消せない。

- 掲載可能なのは集計値のみ。生サンプル(個々のデータレコード)は貼らない
- secrets、API キー、個人情報を含む出力はマスキングしてから引用する
- エラーログを引用する場合は、該当行のみを抜粋し、環境変数やトークンが含まれていないか確認する

## よくある差し戻し

| 差し戻し | 原因 |
|---|---|
| TOO_CONCRETE | 生ログ、生データの本文貼り付け、テスト出力の全文引用 |
| TOO_ABSTRACT | 対応表なし、「うまくいった」だけの結論、再現手順の欠落 |
| 差し戻し(#18) | 期待値が実装出力由来(仕様ではなく実装に合わせたテスト)の疑い |
