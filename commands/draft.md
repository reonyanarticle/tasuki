# /tasuki:draft

このセッションは親 issue の起票支援を行う。
目的は、**起票者の書き方のスキルに依存せず、受理ゲートを一発で通る粒度の親 issue を作る**ことである。
粒度の目盛りを新しく作るのではなく、受理ゲートが使うのと同じ契約の目盛りを、書く前に引く(判定の後出しを対話の前倒しに置き換える)。

## 0. 契約の読み込み

`.tasuki/profile.yaml` を読む。なければ `/tasuki:loop-init` を案内して中断する。
契約の `gates.intake.phase` が指すフェーズの `receives` 定義(waiting_level / too_abstract_signals / too_concrete_signals)と、`parent_issue_required_fields` を控える。
以後の下書きと自己判定はこの2つだけを基準にする(このコマンド独自の基準を持たない。基準が2つあると、ここを通ったのにゲートで落ちる)。

## 1. 要望の受け取り

`$ARGUMENTS` があればそれを生の要望として使う。
なければ「何をしたいか」を1文で尋ねる。
整った文章を求めない(整えるのはこのコマンドの仕事である)。

## 2. 背景の裏取り(リポジトリを読む)

要望に含まれる現状認識を、コードを読んで検証する(例:「金額を float で持っている」と言われたら、実際の型を確かめる)。
裏取りの結果が要望の前提と食い違ったら、起票を進める前にその食い違いを示す(事実と違う背景から作った issue は、分割も実装もずれたまま走る)。
背景欄は、この裏取りで確認できた事実だけで書く(確認できなかった前提は、推測として書かず質問に回す)。

## 3. 質問(コードから導けない欄だけ)

リポジトリから導けない欄だけを、まとめて1回で質問する。

- **価値**:なぜ今やるのか、放置すると何が起きるか
- **予算(コスト上限)**:反復回数や時間の上限
- **完了の定義**:どこまでできたら閉じてよいか

質問の際、契約の承認サイズのシグナル(完了の定義が1回のレビューで判断できる範囲を超えていないか)を意識し、範囲が大きすぎると感じたら分割起票(親を2つに分ける)を提案する。

**実装方式は本文に書かない。**
親 issue の待ち位置は「解き方は未指定」であり、実装方式を書くと受理ゲートで TOO_CONCRETE になる。
起票者が実装方式に言及したら(「ライブラリ X で」「テーブルを分けて」等)、本文から外し、**参考メモ**として控える(手順6で issue コメントに落とす。設計は分割役と実装役の仕事であり、要件と混ぜない)。

## 4. 下書きの組み立て

契約の `parent_issue_required_fields` の全欄を `## 見出し` として含む本文を組み立てる。
文体は宣言的に、曖昧語(「適切に」「柔軟に」等)を使わない。

## 5. 事前審査(受理ゲートと同じ目盛り)

下書きを `receives` 定義と自分で照合し、判断が割れる場合は `tasuki-gate-reviewer`(opus)に事前審査させる(渡すのは下書きと `receives` 定義のみ)。
これは正式な受理ゲートではない:**ラベルは付けず、verdict も issue に残さない**(起票後の初回 `/tasuki:loop` が正式に判定する。事前審査はあくまで起票前の助言であり、通過の記録を先取りしない)。
差し戻し相当なら、理由を示して手順3〜4をやり直す(反復は3回まで。それ以上は割れている論点を示して人間の判断に委ねる)。

## 6. 起票

完成した下書きを提示し、**起票者の確認を得てから** `gh issue create` する(勝手に起票しない)。
参考メモ(実装方式への言及)があれば、起票直後に「参考メモ(要件ではない。分割と実装の判断材料)」として issue コメントに1件残す。
`/tasuki:loop` は起動しない(起動は人間の明示による。次の一手として案内だけする)。

## 7. 判定例の提案(任意)

起票した親が後日受理ゲートを通ったら、その本文と verdict は判定例(`tasuki:baton-contract` の目盛り合わせ fixture)の候補になる。
起票時にその旨を1行案内する(使うほど契約の目盛りが安定する)。
